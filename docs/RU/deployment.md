# Развертывание проекта Dejavue

Dejavue — шаблон (cookiecutter-проект) для создания монолитных приложений на
Django + Inertia + Vue/React. Если вы создали свой проект из этого шаблона с
помощью [cruft](https://github.com/cruft/cruft), данная инструкция поможет вам
развернуть его в продакшене.

## Как работает деплой

Приложение представляет собой **один Docker-контейнер** (монолит):

- **Django + Gunicorn** — бэкенд, слушает порт `8000` внутри контейнера;
- **nginx** — фронтовый прокси, слушает порт `8081`, раздает статику и медиа,
  проксирует запросы на Gunicorn;
- **supervisord** — процесс-менеджер, держит оба процесса в живых;
- **Vite/статикa** — собирается на этапе сборки образа и раскладывается
  `collectstatic`'ом в `/app/static/`.

## Требования

- Docker 24+ на сервере;
- доменное имя, на которое указывает A-запись на ваш сервер;
- доступ к реестру образов (или прямая сборка на сервере).

## Переменные окружения

Перед запуском задайте переменные окружения. Значения по умолчанию описаны в
`.env.example`:

| Переменная     | Назначение                          | По умолчанию             |
|----------------|-------------------------------------|--------------------------|
| `SECRET_KEY`   | Секретный ключ Django               | `django-insecure-secret` |
| `DEBUG`        | Режим отладки (`true`/`false`)      | `false`                  |
| `ENVIRONMENT`  | `production` / `development`        | `production`             |
| `DATABASE_URL` | URL подключения к БД                | SQLite (`db.sqlite3`)    |

> **Важно:** никогда не используйте секретный ключ по умолчанию в продакшене.
> Сгенерируйте его, например: `python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"`.

По умолчанию используется SQLite, но для продакшена рекомендуется отдельный
PostgreSQL, подключение задается через `DATABASE_URL` вида
`postgres://user:password@host:5432/dbname`.

## Сборка образа

Сборка происходит в несколько этапов (multi-stage):

```sh
docker build -t myapp:latest .
```

В процессе сборки Dockerfile:

1. ставит Python-зависимости (`uv pip install`);
2. собирает фронтенд (`npm run build`);
3. выполняет `migrate` и `collectstatic`.

Если миграции нужно выполнить отдельно (например, когда база общая и доступна
только из продакшена), запустите их вручную:

```sh
docker run --rm \
  -e SECRET_KEY=... \
  -e DATABASE_URL=... \
  myapp:latest python manage.py migrate --no-input
```

## Запуск контейнера

Контейнер слушает порт `8081` (nginx). Сопоставьте его с нужным портом хоста:

```sh
docker run -d \
  --name myapp \
  --restart unless-stopped \
  -p 8081:8081 \
  -e SECRET_KEY="ваш-секретный-ключ" \
  -e DEBUG=false \
  -e ENVIRONMENT=production \
  -e DATABASE_URL="postgres://user:pass@host:5432/dbname" \
  -v myapp_media:/app/media \
  myapp:latest
```

- `-v myapp_media:/app/media` — том для пользовательских файлов (медиа), чтобы
  они не терялись при пересоздании контейнера;
- чтобы сразу отдать сайт на 80-й порт, используйте `-p 80:8081`.

Проверьте, что приложение работает:

```sh
curl -I http://localhost:8081
```

## Обновление проекта из шаблона (cruft)

Так как проект создан через cruft, в его корне лежит файл `.cruft.json` — он
связывает ваш проект с шаблоном. Обновления шаблона подтягиваются командой:

```sh
cruft update
```

Полезные флаги:

- `cruft update --skip-apply` — только посмотреть изменения, не применять;
- `cruft diff` — показать расхождения между проектом и шаблоном;
- `cruft check` — проверить, есть ли новые обновления шаблона.

Обновление может затронуть файлы, отвечающие за деплой: `Dockerfile`,
`deploy/nginx.conf`, `deploy/supervisord.conf`, `.env.example`, а также
`skills/deployment/`. После `cruft update`:

1. изучите diff (`cruft update --skip-apply`, затем `git diff`);
2. при необходимости скорректируйте изменения под свой проект;
3. пересоберите образ: `docker build -t myapp:latest .`;
4. пересоздайте контейнер и проверьте работоспособность.

## Рекомендации для продакшена

- Храните секреты не в команде `docker run`, а в переменных окружения CI или
  секретах вашего хостинга (или через файл `.env` с `--env-file`).
- Используйте отдельный PostgreSQL и прокидывайте его через `DATABASE_URL`.
- Выносите `media/` на постоянный том.
- TLS (HTTPS) организуйте на хосте: nginx/Traefik/Caddy перед контейнером,
  пробрасывая запросы на порт `8081`.
- Убедитесь, что `ALLOWED_HOSTS` в `settings.py` не равен `'*'` в проде.
- Следите за логами: Gunicorn и nginx пишут в `stdout`/`stderr` контейнера
  (`docker logs -f myapp`).

## Решение проблем

- **Порт занят** — `listen 8081` уже используется на хосте: поменяйте маппинг
  (`-p 8082:8081`) либо порт в `deploy/nginx.conf`.
- **Ошибки прав nginx** — все временные пути nginx вынесены в `/tmp`
  (`client_body_temp_path`, `proxy_temp_path`, `pid`), процессы идут под
  непривилегированным пользователем `django`. Если ошибки всё же появились,
  проверьте, что тома (`media/`) доступны этому пользователю.
- **Не обновляется статика/фронтенд** — фронтенд собирается на этапе сборки
  образа. После изменения фронтенда обязательно пересоберите образ, а не просто
  перезапускайте контейнер.
